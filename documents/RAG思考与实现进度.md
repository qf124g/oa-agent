# RAG 思考与实现进度

本文档整理近期关于 RAG（检索增强生成）的讨论沉淀，以及当前项目知识库 RAG 的实现进度。

## 一、对 RAG 的思考

### 1. 知识库「对话知识沉淀」的健康度检查

健康度检查的本质是回答四个问题：沉淀进去的知识**有没有用、准不准、全不全、新不新**。一般从以下维度展开。

#### 1.1 内容质量维度（入库时把关）
- **重复度**：新沉淀知识与已有知识做语义相似度比对，超过阈值（如 cosine > 0.9）判重复，提示合并而非新增。
- **完整度**：知识是否包含完整上下文（适用角色、前提条件、操作步骤），避免孤立碎片被沉淀。
- **规范性**：是否符合既定模板/分类，字段（title/category/来源）是否齐全。
- **敏感/错误过滤**：是否含明显错误信息或不该进入知识库的内容。

#### 1.2 检索质量维度（效果健康度，最关键）
- **命中率/覆盖率**：抽样真实用户问题，统计能命中知识（top-k 相似度达阈值）的比例。
- **相关性**：检索到的 top-k 里真正回答问题的占比，可用 LLM 对「问题—知识」做相关性打分。
- **相似度分数分布**：top-k 分数整体偏低说明知识覆盖不足。
- **无应答率**：助手走内部兜底（未命中知识库）的占比，是覆盖缺口信号。

#### 1.3 生命周期维度（存量健康度）
- **活跃度**：每条知识被检索/命中的频次，长期零命中的「冷知识」标记为待归档或更新。
- **时效性/冲突**：同主题多条知识检测是否互相矛盾，结合制度更新时间判断是否过时。
- **来源溯源**：每条知识能追溯到来源（哪次对话、谁确认、何时入库）。

#### 1.4 运营闭环维度
- **沉淀成功率**：对话 → 沉淀中需人工确认/被驳回的比例。
- **用户反馈**：点踩/「回答不满意」标记归类到对应知识，作为低质量知识负面信号。

#### 1.5 落地建议（结合本项目）
- 复用现有向量索引做去重（沉淀时检索 top-1，超阈值提示重复）。
- 增加离线健康度脚本或 CLI，遍历知识条目统计各维度指标。
- LLM 相关性评估：抽 N 条「问题—检索结果」打分，输出召回/准确率。
- 用 AntV 出健康度看板（建议 ≤5 张图：覆盖缺口、低分召回、冷知识占比、去重拦截、活跃度分布）。
- 可量化总分（加权和）：`健康度 = 0.3×内容质量 + 0.35×检索质量 + 0.2×覆盖度 + 0.15×活跃/时效`，其中检索质量权重最高。

### 2. 当前知识库实现 vs 生产级项目区别

#### 2.1 核心结论
当前实现是「演示/教学级 MVP」，跑通了 RAG 最小闭环（存文档 → 切片 → 向量化 → top-k 检索 → 喂给 LLM）；生产级是把每一环都换成**可持久化、可扩展、可观测**的工程实现。

#### 2.2 差异对比

| 维度 | 当前（MVP） | 生产级 |
|---|---|---|
| 存储 | 内存 Map，重启即丢（恢复 seed） | 数据库 + 对象存储 + 独立向量库 |
| 向量检索 | 内存数组 + 暴力余弦 top-k（k=4） | 向量库 ANN 索引（HNSW/IVF/PQ），亿级低延迟 |
| 过滤查询 | 基本只有纯向量相似度 | 元数据过滤、标量 + 向量混合查询 |
| 切块策略 | 固定 500 字、句号/分号断句 | 多策略（结构/语义/父子 chunk，可配 size+overlap） |
| 嵌入 | 单一 text-embedding-v3（DashScope） | 多模型、模型路由、多模态 |
| 检索质量 | 单路向量 + 拼接 | 混合检索 + RRF 融合 + reranker + query 改写/HyDE |
| 数据一致性 | knowledge.updated 事件 + contentHash 增量 | 消息队列异步流水线、全量/增量、版本管理、事务 |
| 扩展性 | 单机单进程，无法多实例共享 | 无状态服务 + 独立存储，可水平扩容 |
| 可观测/评估 | 几乎没有 | 监控/日志、RAG 评估（RAGAS）、灰度、A/B |
| 安全/多租户 | 单租户、无细粒度权限 | 多租户隔离、文档级权限、审计 |

#### 2.3 关键差异本质
1. **持久化 vs 易失**：内存存储重启丢数据是最大命门，生产级底线是知识永不因进程重启丢失。
2. **暴力检索 vs ANN 索引**：暴力余弦是 O(N) 全量比对，靠向量库 ANN（HNSW）降到亚线性，是能否上规模的分水岭。
3. **单一召回 vs 多路召回 + 重排**：向量对专有名词/编号/缩写弱，需加 BM25 关键词召回融合，再上 reranker。
4. **切块粗糙 vs 精细化**：固定 500 字会硬切制度、断裂上下文，生产级按文档结构切分更贴近语义边界。
5. **无评估 vs 持续评估**：无法量化检索好坏，生产级用 RAGAS 等离线评估持续跑分回归。

#### 2.4 一句话总结
实现了 RAG 的「正确骨架」，且 contentHash 增量同步、事件驱动实时同步的思路不输生产；缺的是外围工程能力。改造优先级：① 持久化 → ② 接向量库 → ③ 混合检索 + reranker → ④ 评估闭环 → ⑤ 多租户/权限/监控。

### 3. 混合检索 + Reranker

混合检索和 Reranker 是生产级 RAG 提升「找到相关内容并排准」的两步增强，解决不同问题。

#### 3.1 混合检索（Hybrid Search）
单一向量召回对专有名词、精确编号、缩写不敏感（如「编号 2024-01」）。生产级再加一路关键词检索（BM25），两路并行召回后融合：

| 召回方式 | 擅长 | 弱项 |
|---|---|---|
| 向量检索（语义） | 同义改写（请假 ≈ 休假） | 精确字符串、编号、专有名词 |
| BM25（字面） | 精确匹配：编号、人名、术语 | 同义改写、语义泛化 |

融合常采用 **RRF（Reciprocal Rank Fusion）**：不比分数绝对值，只比各自排名，取排名倒数加和综合排序，两路短板互相补足。

#### 3.2 Reranker（重排）
向量/BM25 都是「粗筛」，用双塔模型各自独立编码丢失交互信息（否定、转折、指代）。Reranker 用**交叉编码器（cross-encoder）**把「问题 + 文档」拼一起逐对打相关性分数，更准但慢，所以只跑在粗筛后的 topN 上。

#### 3.3 与现状链路对应
- 现状：`query → 向量 top-k(k=4) → 拼给 LLM`
- 完整：`query → 向量召回 + BM25 → RRF 融合 → (候选20) → reranker 精排(top5) → 拼给 LLM`

一句话总结：混合检索解决「找回相关内容别漏」（召回率），reranker 解决「挑最相关的排前面」（准确率），是生产级 RAG 的标配组合。

## 二、目前 RAG 实现进度

### 现状架构摘要
内存 Map 存文档 + 向量索引（contentHash 增量同步）+ 上传事件 knowledge.updated 实时同步。

### 已完成能力
- **多格式解析**：txt/md（UTF-8）、pdf（pdf-parse）、docx（mammoth）。
- **文本切块**：500 字符/块，长段落按句号/分号断句。
- **向量化**：OpenAI 兼容 text-embedding-v3（DashScope）。
- **检索**：余弦相似度 top-k（默认 k=4）。
- **增量同步**：contentHash 文档级增量更新，删除文档同步移除。
- **事件驱动**：写操作（add/delete/upload）后发 knowledge.updated 事件触发实时索引同步。
- **启动加载**：启动扫描 backend/seed/knowledge 加载 PDF/MD 文档。
- **上传限制**：文档 10MB；pdf-parse 需 Node ≥ 20.16（项目用 Node 20.20.2）。
- **检索优先级**：信息类问题（what/why/how/介绍/解释）优先走知识库，无结果才用内部知识。
- **流式渲染**：Markdown/GFM/复杂公式/图表渐进渲染。

### 尚未实现（对标生产级待办）
- 持久化存储（数据库 + 对象存储）
- 接入向量数据库（ANN 索引）
- 混合检索（向量 + BM25 + RRF）+ Reranker
- RAG 评估闭环（如 RAGAS）
- 多租户隔离 / 文档级权限 / 审计
- 健康度检查模块与看板
